# ARCnet Spatial Architecture — CE-W01 Geometry v0.2

## Purpose

This specification defines the additive CE-W01 Spatial Architecture contract for ARCnet.

It extends, but does not rewrite, the already-certified Geometry v0.1 contract in:

~~~text
docs/specs/geometry/arcnet-coordinate-frame.md
~~~

Geometry v0.1 remains controlling for the normalized stellar frame, sovereign origin, cube hull, stella-octangula tetrahedral subsets, common octahedral interior, optional icosahedral embedding, rigid transport, projection boundaries, geometry-free operation, and falsification invariants F1–F10.

Geometry v0.2 introduces four additional architectural separations:

1. independently typed coordinate families;
2. bounded and explicitly owned orientation frames;
3. source-owned, domain/profile-scoped semantic correspondence;
4. explicit logical-to-physical topology mapping.

The central rule is:

> **Position may carry a declared, source-owned correspondence inside a bounded profile. Position does not self-authenticate that correspondence and does not self-grant authority.**

Nothing in this specification authorizes Geometry to redefine doctrine, identity, capabilities, governance, recognition, economics, protocol finality, or the canonical module registry.

The existing stellar geometry remains intact under the coordinate-family identifier:


F1–F10 remain unchanged.

v0.2 layers additional coordinate, orientation, correspondence, and topology machinery above those verified fundamentals. It does not rewrite them.

## Governing spatial laws

### Registry before projection

A renderer may display registered information.

Rendering cannot manufacture the information being displayed.

### Coordinate before correspondence

A mathematical address exists independently of any symbolic, cultural, practical, application-owned, or practitioner-owned correspondence attached to it.

### Correspondence before presentation

Presentation may render an existing correspondence.

It cannot silently infer one from position, distance, direction, symmetry, adjacency, color, animation, or visual resemblance.

### Authority remains external

Geometry and correspondence are informational and presentational structures.

They are never independent authorization mechanisms.

### Logical topology is not physical topology

A logical ARCnet edge does not establish that a processor, network, quantum device, or other hardware substrate physically contains the same edge.

### Geometry-free equivalence is mandatory

Any operationally relevant state represented geometrically must remain inspectable and usable without a 2D or 3D scene.

## Coordinate-family registry

ARCnet Spatial Architecture recognizes independently typed mathematical address spaces.

The initial coordinate families are:

~~~text
flower-lattice-2d
stellar-frame-3d
~~~

A coordinate-family identifier declares which mathematical address space owns a coordinate.

Application state, semantic correspondence, camera pose, device pose, geographic position, astronomical orientation, physical implementation, or hardware mapping must not silently mutate canonical addresses.

### stellar-frame-3d

`stellar-frame-3d` is the existing normalized Euclidean Geometry v0.1 frame.

Its mathematical contract remains defined by `arcnet-coordinate-frame.md` and its existing machine-readable companion artifacts.

### flower-lattice-2d

`flower-lattice-2d` is a first-class ARCnet coordinate family.

It is not merely a decorative Hope overlay.

Its mathematical substrate is a triangular/hexagonal center lattice generated by equal-radius overlapping circles.

This defines a mathematical coordinate family.

It does not, by itself, ratify any historical, spiritual, metaphysical, cultural, application, or authority interpretation of the geometry.

## Flower lattice — exact planar family

Let nearest-neighbor center spacing be normalized to:

~~~text
1
~~~

Define canonical basis vectors:

~~~text
b_q = (1, 0)

b_r = (1/2, sqrt(3)/2)
~~~

Every Flower lattice center has an integer axial address:

~~~text
(q, r) ∈ Z²
~~~

Its exact planar position is:

~~~text
P(q, r) = q b_q + r b_r
~~~

therefore:

~~~text
P(q, r) =
(
  q + r/2,
  (sqrt(3)/2) * r
)
~~~

The canonical Flower address is the integer pair `(q,r)`.

Floating-point screen coordinates are derived projections of that address and must not replace it as the canonical lattice address.

### Flower origin

The canonical Flower origin is:

~~~text
F(0,0) = (0,0)
~~~

Its exact planar lift is:

~~~text
L(F(0,0)) = (0,0,0)
~~~

This common origin does not establish mathematical identity between the full Flower lattice and the stellar solids.

### Six nearest neighbors

The six nearest-neighbor axial offsets are:

~~~text
(+1,  0)
(-1,  0)
( 0, +1)
( 0, -1)
(+1, -1)
(-1, +1)
~~~

For any canonical address `(q,r)`, each of these offsets produces a center exactly one normalized Euclidean unit away.

This six-neighbor relation defines the baseline Flower logical adjacency graph.

Logical adjacency remains distinct from runtime connectivity and physical connectivity.

### Overlapping-circle radius

For the canonical overlapping-circle construction:

~~~text
circle radius = 1
nearest-neighbor center spacing = 1
~~~

A neighboring center therefore lies on the circumference of the adjacent equal-radius circle.

This is an overlapping-circle construction.

It is not a non-overlapping circle-packing contract.

## Shell distance and finite windows

Define axial shell distance from the origin:

~~~text
d(q,r) = max(
  abs(q),
  abs(r),
  abs(q+r)
)
~~~

For shell number `n > 0`:

~~~text
shell_count(n) = 6n
~~~

The cumulative number of lattice centers through shell `n` is:

~~~text
window_count(n) = 1 + 3n(n+1)
~~~

Therefore:

~~~text
n = 0  ->  1
n = 1  ->  7
n = 2  -> 19
n = 3  -> 37
~~~

The initial finite-window identifiers are:

~~~text
seed-7:
d(q,r) <= 1

flower-19:
d(q,r) <= 2
~~~

These are ARCnet project names for finite views of the exact lattice.

They do not assert universal historical terminology or metaphysical interpretation.

## Nine-emanation boundary

Nine-emanation structures, where used by an Arcanum domain or semantic source, are semantic-profile candidates.

They are not Flower lattice cardinality.

An implementation must not alter the exact Flower cumulative sequence:

~~~text
1, 7, 19, 37, ...
~~~

to force a nine-element symbolic structure.

A nine-part semantic structure does not manufacture a ninth lattice node, application, module, authority, governance role, recognition state, economic role, or protocol object.

## Exact planar 2D-to-3D lift

One exact relation between the Flower plane and three-dimensional Euclidean space is ratified in v0.2:

~~~text
L(x,y) = (x,y,0)
~~~

Therefore:

~~~text
L(P(q,r)) =
(
  q + r/2,
  (sqrt(3)/2) * r,
  0
)
~~~

This is an exact planar embedding in three-dimensional Euclidean coordinates.

It preserves planar pairwise distances.

It does not establish that `flower-lattice-2d` is mathematically identical to:

- the normalized cube;
- either tetrahedral subset;
- the stella octangula;
- the common octahedral interior;
- the optional icosahedral embedding;
- another Geometry v0.1 solid or overlay.

Visual resemblance, shared centers, coincident individual points, symmetry, symbolic lineage, or project vocabulary are insufficient to establish such identity.

Any stronger Flower↔stellar relation must be:

1. explicitly typed;
2. mathematically derived;
3. represented as a registered transform or correspondence;
4. supplied with provenance and status;
5. machine-falsified before ratification.

Candidate future relation kinds may include:

~~~text

~~~

Until separately verified, their status remains research.

A `semantic-root` North means North as declared by its owning semantic/domain context.

It does not claim that the same direction is geographic north, device-forward, astronomical north, scene-up, or a universal metaphysical direction.

There is no requirement for one universal semantic North across all ARCnet contexts.

## Logical topology


It is not a physical hardware claim.

## Semantic, execution, and physical graph separation

ARCnet must distinguish at least:

~~~text
semantic/correspondence graph
execution graph
physical graph
~~~

The semantic/correspondence graph records registered meanings and source-owned relationships.

The execution graph records runtime communication and capability-permitted paths.

The physical graph records actual processors, qubits, memories, network links, channels, coupling edges, or other hardware relationships.

These graphs may be mapped to one another.

They must never be presumed identical.

Flower adjacency does not automatically create an executable call path.

An executable path does not automatically create a physical edge.

A semantic relation does not automatically create either one.

## Logical-to-physical topology boundary

The required hardware boundary is:

~~~text

        |
        v

        |
        v
hardware-specific topology adapter
        |
        v

~~~

The placement/routing compiler may request locality or adjacency preferences.

The hardware-specific topology adapter is authoritative about what the target substrate actually provides.

A measured mapping result should distinguish:

~~~text
realized logical relations

unmappable logical relations
physical edges actually used
mapping cost
measurement or calibration context
adapter and hardware provenance
~~~

A logical edge absent from the physical graph must not be silently represented as a physical edge.

It must instead be routed or explicitly reported unmapped.

The topology adapter may not invent physical connectivity to satisfy ARCnet ontology.

## Falsification invariants

Geometry v0.1 falsification invariants F1–F10 remain controlling and unchanged.

The following invariants are additive.

### F11 — Flower basis and six nearest neighbors

For any tested canonical Flower address, each of the six defined neighbor offsets must map to a Euclidean center exactly one normalized unit away within the verifier's declared numerical tolerance.

The configured basis must be equivalent to:

~~~text
b_q = (1, 0)
b_r = (1/2, sqrt(3)/2)
~~~

### F12 — exact shell and window counts

The verifier must establish:

~~~text
window_count(0) = 1
window_count(1) = 7
window_count(2) = 19
window_count(3) = 37
~~~

For tested `n > 0`, it must also establish:

~~~text
shell_count(n) = 6n
window_count(n) = 1 + 3n(n+1)
~~~

### F13 — axial-address uniqueness

Within every tested finite window, distinct integer axial addresses must map to distinct canonical planar points.

A rendering approximation may not collapse two canonical addresses into one mathematical address.

### F14 — exact planar lift

For every tested Flower point:

~~~text
L(x,y) = (x,y,0)
~~~

The verifier must establish:

~~~text
z = 0
~~~

and preservation of planar pairwise Euclidean distances after the lift.

No stronger Flower↔stellar identity is implied by this test.

### F15 — orientation invariance

Changing an active orientation frame, semantic North, reference root, camera orientation, geographic reference, device pose, astronomical reference, or scene reference must not mutate the canonical Flower axial address.

### F16 — correspondence non-authority

No correspondence mapping may independently create or modify:

~~~text
identity
capability
permission
authority
governance weight
recognition
readiness
worth
score
economic entitlement
protocol finality
~~~

### F17 — correspondence provenance and status

Every active correspondence mapping must contain explicit source/provenance and status information.

Coordinates alone do not satisfy this requirement.

### F18 — geometry-free equivalence

The same operationally relevant state must remain representable when geometric rendering is removed.

Capabilities, authority meaning, state transitions, and provenance must remain unchanged.

### F19 — logical/physical graph separation

A logical adjacency absent from a target physical topology must be represented as routed or unmapped.

It must not be silently treated as a realized physical edge.

### F20 — hardware-hypothesis boundary

Flower-derived hardware topology must remain explicitly marked as a research hypothesis.

The machine-readable Spatial Architecture contract must contain:

~~~text
physicalOptimalityClaim = false
~~~

until empirical evidence and a separate ratification path authorize any stronger claim.
