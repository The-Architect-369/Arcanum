# Architect System Development Method

## Purpose

This document preserves a development-method insight discovered during the first post-Wave-XXIV Creation Era architecture exploration.

It is not yet an amendment to the canonical Architect GPT specification.

## Core correspondence

The candidate mirror is:

> **Arcanum structures human becoming; Architect structures system becoming.**

Arcanum develops the participant through bounded reflection, time, practice, learning, and retrospective recognition.

Architect develops the system by turning human intention and conceptual possibility into bounded work, evidence, verification, and reviewed promotion.

Neither side replaces the human.

The Human Architect remains indispensable to system development because the system cannot legitimately determine its own purpose, ratify its own constitutional changes, or silently promote its own interpretations into authority.

## Candidate development grammar

```text
idea / intuition
      ↓
exploration
      ↓
bounded arc
      ↓
wave integration
      ↓
milestone achievement
      ↓
evidence
      ↓
Human review / ratification / promotion
      ↓
new stable capability
```

This is not intended as an inflexible ceremony. Each level answers a distinct question.

## Idea / intuition

An idea is a possibility, perceived correspondence, problem, need, or creative direction supplied by a human participant or discovered through grounded system analysis.

An idea is not implementation authority.

Architect should preserve promising ideas without representing them as existing capability or canon.

## Exploration

Exploration asks whether the idea survives contact with:

- existing doctrine;
- architecture;
- implementation constraints;
- human experience;
- security and sovereignty;
- economic and governance boundaries;
- evidence from prototypes, simulations, research, or prior work.

Exploration may produce multiple candidate designs.

Its purpose is not to force closure prematurely.

## Arc

An **Arc** is a bounded unit of coherent system development or investigation.

An Arc should have:

- one intelligible purpose;
- a bounded scope and non-scope;
- explicit dependencies;
- concrete questions or implementation targets;
- an evidence/verification condition;
- a clear handoff into the next Arc or Wave gate.

An Arc may be conceptual, architectural, implementation-focused, verification-focused, or embodiment-focused, but its purpose must remain coherent.

## Wave

A **Wave** integrates one or more related Arcs into a meaningful tested capability or resolved design domain.

A Wave should not be defined by an arbitrary number of Arcs.

Its size follows the evidence required to establish the Wave's purpose.

A Wave closes when its constituent Arcs collectively satisfy the Wave's bounded objective and verification requirements.

## Milestone

A **Milestone** represents a meaningful achieved state of the system rather than a calendar checkpoint.

Candidate rule:

> **Arcs complete waves. Waves complete milestones.**

A milestone may require both substrate achievement and visible/human embodiment where the capability is intended to be experienced by participants.

The system should avoid treating technically implemented but unusable/invisible capability as complete when embodiment is part of the intended outcome.

## Evidence

Architect should remain grounded in reality by requiring evidence appropriate to the claim being made.

Evidence may include:

- repository state;
- tests;
- builds;
- device behavior;
- runtime receipts;
- security verification;
- doctrine checks;
- user-visible embodiment;
- design validation;
- protocol finality where actually required.

The type of evidence must match the claimed achievement.

## Human role

The Human Architect is not merely an input source to an autonomous development system.

Human participation is a constitutional and creative boundary.

The human may:

- introduce purpose and intention;
- perceive correspondences;
- reject technically valid but philosophically incorrect outcomes;
- make unresolved design choices;
- authorize repository mutation;
- review evidence;
- ratify canonical changes where authorized;
- decide when exploration has matured enough for implementation.

Architect's role is to increase the human's ability to develop the system coherently, not to replace human judgment.

## Relationship to current Architect lifecycle

The canonical Architect lifecycle currently includes:

```text
GROUND → INSPECT → DIAGNOSE → PLAN → AUTHORIZE → ACT → VERIFY → RECORD
```

The candidate Arc/Wave/Milestone method does not replace that lifecycle.

They operate at different scales:

- **GROUND → ... → RECORD** describes how Architect executes one bounded operation safely.
- **Arc → Wave → Milestone** describes how many bounded operations accumulate into system development.

Candidate nesting:

```text
MILESTONE
  └── WAVE
       ├── ARC
       │    └── GROUND → ... → RECORD
       ├── ARC
       │    └── GROUND → ... → RECORD
       └── ARC
            └── GROUND → ... → RECORD
```

This is a promising correspondence to validate during Creation Era planning.

## Participant applicability

A later Architect application could use the same structured-development grammar to help participants contribute to system growth.

Architect may help a participant turn an idea into:

```text
idea
  ↓
question
  ↓
proposal / Arc
  ↓
bounded work
  ↓
evidence
  ↓
review
  ↓
contribution to a Wave / Milestone
```

This would allow community participation without collapsing contribution into unstructured feature requests or granting contributors unilateral authority.

Exact contribution, governance, entitlement, compensation, or MANA rules remain outside this document.

## Creation Era application

The first major candidate use of this methodology is the eight-point ARCnet topology investigation.

The proposed milestone is to understand and validate the complete 28-edge relationship graph deeply enough to determine whether it should become Module Architecture v2 and an executable ARCnet relationship layer.

Reference edge 01:

- **Arcanum ↔ Nexus**

Future roadmap work should group the other edges into waves and arcs according to dependency and diversity of evidence, not by mechanically assigning one edge to one Arc unless that proves useful.

## Safeguards

This methodology must not become:

- an excuse for Architect to self-ratify;
- a compulsory productivity system for human worth;
- an automatic promotion engine;
- a gamified status ladder;
- a way to infer that more completed work means a more valuable person;
- a replacement for doctrine/governance authority.

It is a **system-development grammar**, not a human-value metric.

## Next gate
